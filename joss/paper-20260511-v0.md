# Static Checking for Safer Clinical Dataframe Pipelines: Design and Evaluation of a TypeScript-Based Data Analysis Framework

## Abstract

### Objective

Clinical data analyses often require many table operations: selecting columns, joining patient and encounter records, reshaping laboratory and vital-sign data, converting strings to numbers or dates, and handling missing values. Small mistakes in these steps can produce incorrect results, especially when errors are not detected until late in the workflow or continue without warning. This study evaluates whether a type-safe dataframe framework can detect common clinical data transformation errors before execution.

### Materials and Methods

We developed Tidy-TS, a TypeScript framework for dataframe transformation, statistical analysis, visualization, asynchronous data processing, and schema-validated data ingestion. Tidy-TS represents each dataframe row as a TypeScript type and updates that type as the dataframe changes. Operations such as `select`, `drop`, `mutate`, `rename`, `summarize`, joins, pivots, row binding, and missing-data handling update the known shape of the data. We evaluated the framework with three test artifacts: a compile-time guarantee audit, runtime boundary-validation tests, and a cross-ecosystem comparison suite using clinical fixtures representing patients, encounters, laboratory results, medications, and vital signs. Equivalent probes were implemented in Tidy-TS, Python/pandas, and R/tidyverse. Each outcome was classified as a compile-time error, runtime error, runtime warning, or silent continuation. Tidy-TS also includes statistical routines, I/O support, asynchronous operations, visualization support, columnar storage, and WebAssembly acceleration. 

### Results

The compile-time audit verified exact output types for common dataframe operations, including unchanged row shape after filtering and sorting, narrowed schemas after selecting or dropping columns, added and replaced columns after mutation, new schemas after summarization and reshaping, join-introduced missing values, row-binding unions, grouping state, and null/undefined narrowing. Invalid operations, including stale column references, invalid join keys, unsafe use of nullable values, invalid post-aggregation references, and shape-incompatible append/prepend operations, were rejected by the TypeScript compiler. Runtime boundary tests confirmed that schema-backed dataframe construction rejected wrong scalar types, missing required fields, null values in non-nullable fields, and invalid categorical values, while preserving valid nullable schemas. Cross-ecosystem probes showed that many errors rejected before execution by Tidy-TS were detected only at runtime in pandas or tidyverse, and that missing values, invalid comparisons, type coercions, join-introduced missingness, and window-function boundary values often continued silently in dynamic workflows. Type-checker performance testing showed that the compile-time audit checked in approximately 1.2 seconds, schema-width examples from 5 to 100 columns checked in approximately 1.2–2.4 seconds, and deeply chained mutation pipelines reached a TypeScript depth limit between 33 and 35 consecutive transformations.

### Conclusion

Tidy-TS demonstrates that common clinical dataframe errors can be detected earlier by making table shape, column types, join effects, and missing values visible to the programming language before code runs. This approach does not replace runtime validation or statistical review, but it shifts a meaningful class of clinical data transformation errors from late detection or silent continuation to earlier detection during development.

## Background and Significance

Clinical data work depends on tables. Patient demographics, encounters, diagnoses, medications, laboratory results, vital signs, claims, and device streams are usually transformed through a series of table operations before they are analyzed. A typical workflow may read data from files or databases, select a subset of columns, join several tables, convert strings into numbers or dates, reshape long data into wide form, group records by patient or encounter, summarize measurements, and then pass the result into a statistical model or dashboard.

These steps are routine, but they are also a common source of error. A column may be misspelled. A column that existed early in a pipeline may no longer exist after a `select`, `drop`, `summarize`, or `pivot` step. A left join may introduce missing values into fields that previously looked complete. A string may be used where a number was expected. A missing laboratory value may be skipped, propagated, converted, or silently excluded depending on the language and function being used. These problems are especially important in biomedical informatics because clinical data are often sparse, heterogeneous, and repeatedly reshaped.

Most clinical data analysis is performed in dynamic dataframe environments such as Python/pandas or R/tidyverse. These tools are powerful and widely used, but many errors are discovered only when code runs. Some failures are clear because the program stops with an error. Others are harder to detect because the program continues and produces a plausible result. Silent continuation is particularly risky in clinical data workflows because an apparently valid table may be used downstream for cohort definition, quality measurement, modeling, visualization, or decision-support evaluation.

The central question in this study is whether some of these errors can be detected earlier. Rather than waiting until code runs, a programming language can sometimes check that an operation is valid before execution. This requires the language to know what columns exist, what types those columns contain, and whether values may be missing. In ordinary dataframe use, this information is usually known by the analyst but not always represented in a way that the programming environment can enforce.

Tidy-TS was designed to address this gap for TypeScript-based data workflows. TypeScript is widely used in clinical applications, dashboards, APIs, web tools, and data-facing software systems, but it has not traditionally been treated as a primary language for statistical data analysis. Tidy-TS brings dataframe transformation, statistical functions, visualization, schema validation, asynchronous operations, and multi-runtime support into the TypeScript ecosystem. Its key design choice is that dataframe operations update the known shape of the data as the pipeline changes. For example, after a column is dropped, later code cannot refer to it. After a left join, fields from the right table are treated as possibly missing. After converting a string to a number in a way that can fail, the result is treated as numeric or null until the null case is handled. 

This study evaluates Tidy-TS as an approach to safer clinical dataframe programming. The goal is not to show that TypeScript is generally superior to Python or R. The goal is narrower: to determine whether a type-aware dataframe design can detect a meaningful class of clinical data transformation errors earlier than conventional dynamic dataframe workflows.

## Objective

The objective of this study was to develop and evaluate a type-safe dataframe framework for clinical data workflows, with emphasis on detecting common table transformation errors before execution.

The study focused on four practical questions:

1. Can a dataframe library track column names, column types, missing values, and join effects across common clinical data transformations?

2. Can the programming environment reject invalid downstream operations before the code runs?

3. How do equivalent clinical data errors behave in Tidy-TS, Python/pandas, and R/tidyverse?

4. What are the practical limits of this approach, including runtime validation needs, TypeScript escape hatches, and type-checker performance?

## Materials and Methods

### System Design

Tidy-TS is a TypeScript framework for working with tabular data. It provides a dataframe abstraction for arrays of objects, which are common in JavaScript and TypeScript applications. Each dataframe has a row type that describes the columns available in that dataframe and the type of value in each column.

For example, a dataframe with patient identifiers, names, and ages has a row type containing those fields. When an operation changes the dataframe, the row type changes as well. Selecting columns narrows the row type. Dropping columns removes fields. Mutating data adds or replaces fields. Grouping and summarizing produce a new row type. Joins combine row types and mark fields as possibly missing when the join can introduce missing values.

The framework includes dataframe operations inspired by common R and Python workflows, including filtering, sorting, selecting, dropping, renaming, mutating, grouping, summarizing, joining, pivoting, binding rows, filling missing values, and extracting columns. It also includes statistical functions, hypothesis tests, visualization support, asynchronous transformations, schema-backed data ingestion, and support for browser, server, and notebook environments. 

### Schema Validation at Data Boundaries

Static checking can only reason about data after the program has a trustworthy description of the input. For external data, Tidy-TS supports runtime schema validation using Zod. A schema can be supplied when creating a dataframe. The schema checks the input rows at runtime and produces a dataframe whose TypeScript row type is inferred from the schema.

This separates two safety problems. At the boundary, runtime validation checks whether incoming data match the expected structure. Inside the pipeline, TypeScript checks whether later transformations are valid given the known structure of the dataframe.

### Compile-Time Guarantee Audit

We created a compile-time audit file to test the static behavior of the dataframe API. This file type-checks but is not intended to run. It uses type-level assertions to verify the exact output type of dataframe operations. It also uses `@ts-expect-error` comments to verify that invalid programs are rejected.

The audit covers schema-preserving operations, schema-narrowing operations, schema-extending operations, schema-replacing operations, null/undefined introduction, null/undefined removal, grouping state, chained pipelines, schema-derived construction, and documented escape hatches. Examples include verifying that `select` returns only selected columns, `drop` removes dropped columns, `mutate` adds or replaces columns, `summarize` produces a new row type, joins mark unmatched-side fields as possibly missing, and `removeNull` or `replaceNull` narrows nullable fields after explicit handling. 

### Runtime Boundary Tests

We created runtime validation tests as a companion to the compile-time audit. These tests confirm behavior that cannot be proven by static types alone. They test schema rejection for wrong scalar types, missing required fields, null values in non-nullable fields, and invalid categorical values. They also test valid schema acceptance, nullable value preservation, append/prepend behavior, fill-forward/fill-backward edge cases, empty dataframe behavior, and runtime behavior for null removal and replacement. 

### Cross-Ecosystem Error Comparison

We created a comparison suite using clinical-style test fixtures. The fixtures include patients, encounters, laboratory results, medications, and vital signs. Each test represents a common clinical data transformation mistake, such as a misspelled patient identifier, a stale encounter column after summarization, a pivoted vital-sign column that does not exist, arithmetic on a nullable laboratory value, a join that introduces missing data, or an invalid categorical value.

Equivalent probes were implemented in Tidy-TS, Python/pandas, and R/tidyverse. Each probe was classified by outcome:

* **Compile-time error:** rejected before execution.
* **Runtime error:** program stops when the line executes.
* **Runtime warning:** program warns but continues.
* **Silent continuation:** program continues without error or warning, producing a result that may conflict with the analyst’s intended assumption.

The comparison suite groups errors into categories such as column and schema reference errors, type safety errors, null and missing data errors, and join safety errors. The example comparison file shows clinical fixtures and tests for patients, labs, encounters, and vitals, including compile-time tests for Tidy-TS and runtime probes for Tidy-TS, Python, and R. 

### Type-Checker Performance Measurement

Because the approach relies on TypeScript’s type checker, we measured the cost of checking representative files. Measurements included the full compile-time audit, pipelines with varying schema width, and pipelines with varying chain depth. Chain-depth tests were also used to identify the point at which deeply repeated transformations reach TypeScript’s type-instantiation limit.

### Statistical Function Validation

Tidy-TS includes statistical functions and hypothesis tests. These are separate from the dataframe safety evaluation but are part of the broader framework. Statistical tests are validated against R using randomized test suites that compare test statistics and p-values within a tolerance of 1e-6.

## Results

### Compile-Time Schema Tracking

The compile-time audit showed that Tidy-TS preserved or changed dataframe row types according to the expected behavior of each operation.

Operations that should not change columns, such as filtering, sorting, slicing, shuffling, reordering, and interpolation, preserved the row type. Operations that remove columns, such as `select`, `drop`, and `distinct`, produced narrower row types. Operations that add or replace columns, such as `mutate` and `rename`, produced updated row types. Operations that produce a new table shape, such as `summarize`, `count`, `pivotWider`, `pivotLonger`, and `unnest`, produced new row types.

The audit also verified that joins changed the row type according to join semantics. Inner joins preserved matched fields without adding missingness. Left joins marked right-side fields as possibly undefined. Right joins marked left-side fields as possibly undefined. Outer joins marked non-key fields from both sides as possibly undefined. Joins with column-name collisions exposed suffixed column names and rejected later references to the original ambiguous name.

Missingness was also tracked. Functions such as `lag` introduced `undefined`. Row binding with different schemas marked fields that were not present in all inputs as possibly undefined. Operations such as `removeNull`, `replaceNull`, and `removeUndefined` narrowed types after explicit handling. Fill-forward and fill-backward preserved nullability because leading or trailing missing values may remain. 

### Rejected Invalid Programs

The audit confirmed that invalid dataframe programs were rejected before execution. Examples included selecting or dropping nonexistent columns, using a dropped column after selection, using an old column name after renaming, referencing pre-aggregation columns after summarization, using pivot-consumed columns after reshaping, joining on invalid keys, using nullable values in arithmetic without first handling nulls, calling methods on possibly missing join fields, and appending or prepending rows with missing or incorrectly typed fields. 

### Runtime Boundary Validation

Runtime validation tests confirmed that schema-backed dataframe construction rejected malformed input. Zod schemas rejected rows with wrong scalar types, missing required fields, null values in non-nullable fields, and invalid categorical values. Valid rows were accepted, and nullable schemas preserved null values when allowed.

Runtime tests also confirmed behavior for missing-data edge cases. Fill-forward filled interior and trailing missing values when a prior value existed but left leading nulls unchanged. Fill-backward filled leading missing values when a later value existed but left trailing nulls unchanged. These results support the static decision to preserve nullability after fill-forward and fill-backward rather than claiming all missing values were removed. 

### Cross-Ecosystem Comparison

The comparison suite showed that Tidy-TS detected many common clinical dataframe errors before execution. In the column and schema reference category, Tidy-TS rejected misspelled columns, nonexistent predicate fields, stale names after renaming, dropped columns, post-summarization references, and invalid post-pivot references at compile time. Equivalent pandas and tidyverse programs often failed at runtime, while some schema-narrowing differences continued silently when the dynamic workflow retained columns that the analyst may have assumed were removed. 

In the type safety category, Tidy-TS rejected arithmetic on string columns, numeric aggregation over string columns, comparisons between incompatible values, arithmetic after failed conversion, mixed-type transformations used as numeric values, temporal misuse, numeric functions applied to categorical fields, and invalid categorical comparisons. Equivalent pandas and tidyverse behavior varied by operation: some cases raised runtime errors, some produced warnings, and others continued silently through coercion, empty filters, or missing-value propagation. 

In the null and missing data category, Tidy-TS rejected unsafe method calls, arithmetic, comparisons, aggregations, sorting, lagged-value arithmetic, and pivot-derived arithmetic when values could be null or undefined. Dynamic workflows frequently continued silently, including cases involving NaN/NA propagation, skipped missing values in aggregation, missing boundary values introduced by window functions, and implicit ordering of missing values during sorting. 

In the join safety category, Tidy-TS rejected invalid join keys, misspelled keys, missing post-join columns, unsafe use of join-introduced missing values, comparisons on possibly missing fields, and stale references after suffixing colliding column names. In pandas and tidyverse, invalid join keys generally raised runtime errors, while missingness introduced by left joins frequently continued silently unless explicitly handled. 

### Type-Checker Performance

The type-checker performance script showed that the compile-time audit checked in approximately 1.2 seconds. Representative schema-width pipelines from 5 to 100 columns checked in approximately 1.2–2.4 seconds. Deeply chained mutation pipelines showed a practical limit: approximately 33 consecutive `.mutate()` calls checked successfully, while approximately 35 consecutive calls triggered TypeScript’s deep type-instantiation error. This boundary reflects a host-language limit in TypeScript rather than a runtime limitation of dataframe execution.

### Statistical Function Validation

The framework includes statistical hypothesis-testing routines with typed results, including test names, p-values, effect sizes, test statistics, confidence intervals, degrees of freedom, and alternatives. These routines are validated against R using randomized tests with agreement within 1e-6 for test statistics and p-values.

## Discussion

This study shows that many routine dataframe errors in clinical data workflows can be detected before code runs. The key design is simple: the dataframe carries a description of its columns and value types, and each transformation updates that description. If later code refers to a column that no longer exists, uses a value that may be missing, or treats a string as a number, the compiler can reject the code.

This is important because clinical data pipelines often fail in small, ordinary ways. The problem is rarely that an analyst writes a completely invalid program. More often, an assumption becomes stale. A field is renamed. A join changes completeness. A pivot creates some columns but not others. A summary step removes detailed encounter fields. A missing laboratory reference range becomes part of a calculation. These are the kinds of errors Tidy-TS is designed to surface.

The comparison with pandas and tidyverse should be interpreted carefully. Python and R are mature, powerful, and widely used for clinical data analysis. The point is not that these tools are defective. The point is that their default dataframe workflows often detect errors later because the shape and missingness of the dataframe are not checked by the language before execution. Runtime errors are helpful when they stop the program. Silent continuation is more concerning because it can produce a plausible table that enters downstream analysis.

Tidy-TS also does not eliminate the need for runtime checks. External data must still be validated when loaded. A type-safe pipeline is only as reliable as the data contract at its boundary. For this reason, Tidy-TS combines compile-time checking inside the pipeline with runtime schema validation at input boundaries.

The results also show that TypeScript has practical limits. Type assertions, `any`, and unsafe casts can bypass type checking. Deeply chained transformations can hit the compiler’s type-instantiation limit. These limitations do not invalidate the approach, but they define its scope: Tidy-TS provides strong checks when the typed API is used as designed; it does not make arbitrary TypeScript code sound.

For biomedical informatics, the broader significance is that many clinical data applications already use TypeScript. Web dashboards, data collection tools, APIs, decision-support prototypes, registry interfaces, and real-time clinical systems often contain data transformation logic outside traditional statistical environments. Tidy-TS makes it possible to keep more of that workflow in a single typed environment, reducing the need to export data to a separate analysis language for every transformation and then re-import results into an application.

---

## Limitations

This study has several limitations.

First, the comparison suite uses clinical-style fixtures rather than a large collection of real production pipelines. The fixtures are designed to isolate common dataframe failure modes, but they do not measure the frequency of these errors in routine clinical analytics.

Second, the evaluation measures error detection, not downstream patient outcomes, clinical decision quality, or analyst productivity. A future study should evaluate whether this approach reduces debugging time, improves confidence, or prevents errors in real-world clinical research workflows.

Third, TypeScript contains intentional escape hatches. Users can cast through `unknown`, use `any`, or otherwise bypass the checker. Tidy-TS can document and discourage these patterns, but it cannot prevent all unsafe TypeScript code.

Fourth, static checking does not prove clinical correctness. It can verify that a column exists, that a value is numeric, or that missingness was handled. It cannot prove that a cohort definition is appropriate, that a causal model is valid, that a statistical test is justified, or that clinical concepts are correctly specified.

Fifth, runtime validation remains necessary. External files, database results, API responses, and user-provided data may not match expected schemas. Tidy-TS addresses this with Zod-backed validation, but schema design remains the responsibility of the developer.

Sixth, the type-checker performance results are preliminary. They provide useful evidence about feasibility and TypeScript limits, but they should be repeated across machines, TypeScript versions, Deno versions, and larger synthetic pipelines before making broad performance claims.

---

## Conclusion

Tidy-TS provides a type-safe dataframe framework for TypeScript-based clinical data workflows. By tracking dataframe shape, column types, join effects, grouping state, reshaping results, and missingness through ordinary table operations, the framework detects many common clinical data transformation errors before execution. Runtime schema validation complements these checks at data boundaries. The approach does not replace Python, R, clinical review, or statistical validation, but it offers a practical method for shifting a meaningful class of clinical dataframe errors earlier in the development process.

### Table 4. Type-Effect Catalog

Each dataframe verb produces a predictable change in the row type. The compile-time audit verified these effects using bidirectional type-equality assertions.

| Operation | Type effect | Clinical relevance |
| --- | --- | --- |
| filter, arrange, slice | Preserves row type | Subsetting patients or encounters does not change available columns |
| select | `Pick<Row, Cols>` | Selecting `patient_id` and `age` removes other fields from later use |
| drop | `Omit<Row, Cols>` | Dropping identifiers before analysis removes them from the type |
| mutate (new) | `Row & { col: T }` | Computing `bmi` from `weight` and `height` adds `bmi` to the type |
| mutate (replace) | Column type replaced | Converting `result_value` from string to number changes the column type |
| rename | Key substitution | Renaming `enc_id` to `encounter_id` removes the old name from the type |
| summarise | `GroupKeys & SummaryCols` | Summarizing by `department` removes individual encounter fields |
| pivotWider | New cols from data values | Pivoting vital signs by `measure_name` creates `systolic`, `diastolic` columns |
| leftJoin | Right-side cols → `T \| undefined` | Joining patients to encounters marks encounter fields as possibly missing |
| bindRows | Unique cols → `T \| undefined` | Binding lab and vitals tables marks columns unique to one source as optional |
| lag | Returns `(T \| undefined)[]` | Lagging a lab result introduces `undefined` at the first position |
| removeNull | Removes `null` from column type | After removing null lab values, downstream arithmetic is allowed |
| fillForward | Preserves row type | Leading nulls may remain; the type does not claim null removal |
